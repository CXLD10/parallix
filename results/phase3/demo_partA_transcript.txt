Parallix -- a compiler that checks its own parallelization verdicts

Two kernels. One can be parallelized and one cannot. Parallix has to say which, say why,
and then try to prove itself wrong.

PART A: a parallelizable O(n^2) problem
=======================================

Count the pairs (i < j) with a[i] + a[j] == target, by brute force. The inner loop is
triangular (j starts at i+1) and the result is an integer count.
$ cat examples/count_pairs.plx
    // Demo A - count pairs (i < j) with a[i] + a[j] == target, brute force.
    // Triangular inner loop, integer count reduction. Still O(n^2): parallelism
    // divides the constant factor, it does not change the complexity.
    // Expected verdict: SAFE_AS_REDUCTION.
    kernel count_pairs(a: i32[N], target: i32) -> count: i64 {
        reduce(+) i in 0..N {
            auto j in i+1..N {
                count += select(a[i] + a[j] == target, 1, 0)
            }
        }
    }

Step 1 -- analysis. Parallix compares every pair of array references with a GCD test and
distance analysis it implements itself. Both references read 'a', so nothing conflicts; the only
carried dependence is the count accumulator, which is a licensed reduction.

Step 3 -- try to break it. Parallix runs the sequential code, the loop in reversed order and
in seeded random orders, then the parallel code on 1, 2, 4, 8 and all threads, 20 times each,
across several seeds and sizes that are not multiples of the thread count. If the loop were really
order-independent, nothing should ever differ.

Step 5 -- is it actually faster? Median of 5 runs, sequential vs parallel, measured now.

Be clear about what this is: the algorithm is still O(n^2). Parallelization divides the
constant factor across cores; it does not change the complexity.
